  bad JSON → 400
      ├── respond.js         # new: helpers that send { message, data } with the
  status code
      └── validate.js        # new: shared checks (ObjectId format, required
  fields, type checks)

  Why it's split this way:

  - One model file and one route file per resource. This follows the pattern the
    starter already uses (require('./routes')(app, router)).
  - utils/query.js: the query-parameter rules are identical for users and tasks,
    except the default limit (100 for tasks, unlimited for users). Writing it
    once keeps the two endpoints from drifting apart. It builds the query with
    Mongoose's own find().sort().select().skip().limit() and countDocuments(),
    which requirement 5 asks for.
  - utils/respond.js: every response has to be { message, data }, and errors
    must never pass Mongoose messages through to the client. If it all goes
    through one helper, an internal message can't slip out by accident.
  - The two-way reference logic stays in the route handlers (users.js and
    tasks.js). Each handler checks everything first and only then writes to the
    database, so a request that fails changes nothing. That order is what the
    spec requires.

  One small change I'd make to routes/index.js: give each route file its own
  express.Router(). Right now a single router is passed in and shared, and once
  there are several route files that gets confusing.

  If that looks good, I'll write the models first, then the utils, then the
  routes, then test locally against your Atlas database. You're still on Node
  26, which should be fine for local development. Have you created .env with
  your MONGODB_URI yet?
